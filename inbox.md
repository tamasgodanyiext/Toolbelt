- [ ] Concept candidate: explicit progress state / unit of work. Correctness came from making units of work and their completion explicit: control tower + synchro barrier (productionizing), per-date completion ledger (repartitioning), orphan retry state (late-arriving data), batch identity as `txnAppId` (observability).

- [ ] Telemetry migration: a file archiver consumes the old monitoring table as evidence that processing completed. How can it move to unified input telemetry without changing archive eligibility? Investigate source mapping, multiple consumers, historical coverage and cursor behaviour. Current hypothesis: a compatibility projection can preserve the workflow, but “input observed” must mean enough to permit deletion. Compare candidate files before switching; distinguish dispatched archive requests from confirmed completion. Related: unified observability case.
- [ ] Telemetry migration: a non-streaming file loader both reports successful files and reads the reporting table to allocate its next batch ID. How can it adopt unified telemetry without depending on Spark streaming identity? Define execution identity, retry semantics and per-file counts; separate telemetry failure from file-processing status. Current hypothesis: decouple batch numbering from reporting, then compare successful-file observations during dual reporting. Related: unified observability case and archiver migration.
